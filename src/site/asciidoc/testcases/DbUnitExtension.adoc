= DbUnitExtension
Jeff Jensen

== Overview

link:../apidocs/org/dbunit/junit/jupiter/DbUnitExtension.html[DbUnitExtension]
is a JUnit 5/6 (Jupiter) extension that drives the
link:IDatabaseTester.html[IDatabaseTester] setup/teardown lifecycle
automatically, so a test class doesn't need its own `@BeforeEach`/`@AfterEach`
pair calling `onSetup()`/`onTearDown()`.

NOTE: The extension needs JUnit Jupiter 5.7 or later, the release that added the
newest Jupiter API it calls. dbUnit itself is built and tested against JUnit 6.

Register it with `@ExtendWith(DbUnitExtension.class)`, or with the shorter
`@DbUnitTest`. The test class still holds its own `IDatabaseTester` field —
this is the same composition style as link:IDatabaseTester.html[the
IDatabaseTester guide], just with the lifecycle calls automated instead of
written by hand:

[source,java]
----
@ExtendWith(DbUnitExtension.class)
class AccountRepositoryTest
{
    IDatabaseTester databaseTester;

    AccountRepositoryTest() throws ClassNotFoundException
    {
        databaseTester =
                new JdbcDatabaseTester("org.h2.Driver", "jdbc:h2:mem:example;DB_CLOSE_DELAY=-1");
    }

    @BeforeEach
    void loadDataset() throws Exception
    {
        databaseTester.setDataSet(new FlatXmlDataSetBuilder().build(new File("prep.xml")));
        databaseTester.setTearDownOperation(DatabaseOperation.DELETE_ALL);
    }

    @Test
    void testWithdraw_sufficientBalance_decrementsBalance() { ... }
}
----

`@BeforeEach` methods still run first — configure the dataset and any
operation overrides there. The extension then calls `onSetup()` immediately
before the test method and `onTearDown()` immediately after it, even if the
test method fails or `onSetup()` itself throws.

== Field Discovery

The extension finds the `IDatabaseTester` by scanning the test instance's
fields, including inherited ones:

* The nearest declaring class wins — a field on the test class itself takes
  precedence over one on a superclass.
* That class must declare exactly one non-static field assignable to
  `IDatabaseTester`. No match anywhere in the hierarchy, or two-or-more
  matches at the same class level, both fail fast with a descriptive
  `IllegalStateException` rather than guessing.
* Static fields are ignored.
* Private fields are found; the field's own access modifier doesn't matter.

Field discovery also walks every enclosing test instance, innermost first,
so a `@Nested` test class inherits its enclosing class's tester field.

== Annotation-Driven Configuration

Rather than a `@BeforeEach` method, the dataset and operation can be
declared directly on the class or method with `org.dbunit.annotation` —
`@DbUnitPrep`, `@DbUnitSetUpOperation`, `@DbUnitExpected`, `@DbUnitTearDownOperation`, and
`@DbUnitConfig`. A test that does so no longer runs through the tester's `onSetup()` and
`onTearDown()`: the extension runs a
link:PrepAndExpectedTestCase.html[PrepAndExpectedTestCase] around it instead, which reads the
tester's connection and operations, never its dataset, and writes nothing to it — see
link:annotations.html#lifecycle[The Lifecycle]. It also
unlocks the verification that `@DbUnitExpected` declares, and a `@DbUnitTester`/`@DbUnitTestCase`
field marker in place of the plain-field auto-scan described above. A dataset a `@BeforeEach`
method gave the tester is not set up for such a test: name its file with `@DbUnitPrep`. See
link:annotations.html[DbUnit Annotations] for the full reference.

== Row Count Check

The same link:../components/rowcountcheck.html[RowCountCheck] diagnostic available to
link:PrepAndExpectedTestCase.html[PrepAndExpectedTestCase] applies here too: a baseline is
captured from the connection of the resolved `IDatabaseTester` before the setup operation
changes any data, and verified after `onTearDown()`, failing the test by name when a table's row count moved.
An annotation-driven test's check is its test case's own, captured before its setup operation and
verified after its teardown operation. Verification
is skipped whenever `onTearDown()` itself throws, and also when the test method threw
before reaching it, since either way the database is left in an unknown state and a count
difference would only be noise around the real failure. It is off by default; enable it
with `DatabaseConfig.FEATURE_ROW_COUNT_CHECK` (or `-Ddbunit.rowCountCheck=true`) on the
connection's config, or per class/method with
link:annotations.html#rowcountcheck[`@DbUnitRowCountCheck`].

== Parameter Injection

`DbUnitExtension` also resolves `IDatabaseTester` and `IDatabaseConnection`
parameters on `@Test` and `@BeforeEach` methods, so a test can ask for the
tester or its connection directly instead of reaching through a field:

[source,java]
----
@DbUnitTest
class AccountRepositoryTest
{
    IDatabaseTester databaseTester;

    AccountRepositoryTest() throws ClassNotFoundException
    {
        databaseTester =
                new JdbcDatabaseTester("org.h2.Driver", "jdbc:h2:mem:example;DB_CLOSE_DELAY=-1");
    }

    @Test
    void testWithdraw_sufficientBalance_decrementsBalance(final IDatabaseConnection connection)
            throws Exception
    {
        // connection.getConnection() is the JDBC connection
    }
}
----

A parameter is matched by its declared type exactly: a parameter declared as a
subtype, such as a `JdbcDatabaseTester`, is left to whichever other resolver
supplies it, since the value injected here is not necessarily an instance of
that subtype.

Parameter injection is claimed only for a test that opts into
link:annotations.html[`org.dbunit.annotation`] — one carrying `@DbUnitTest`
or any `@DbUnit*` annotation on the class or method, or a `@DbUnitTester`/
`@DbUnitTestCase` field. A bare `@ExtendWith(DbUnitExtension.class)` class
with only a plain, unannotated `IDatabaseTester` field keeps the
lifecycle-only behavior it has always had and no parameter is claimed for
it, so another extension resolving one of these types on the same test method
is not left competing with a claim here. That
class takes the link:../components/rowcountcheck.html[row count check] baseline,
whether or not the check is enabled, because the setting lives on a connection's
`DatabaseConfig`, from the connection `onSetup()` retrieves, after the tester's
`IOperationListener#connectionRetrieved()` has run, so enabling the check there works
and capturing the baseline opens no connection of its own. For that it wraps the
tester's listener for the test, forwarding every callback to it unchanged, and puts
it back afterward. The connection `onSetup()` retrieves stays the listener's to close
or to keep open, as in 3.5.0. When `onSetup()` cannot be relied on to retrieve a
connection - a `NONE` setup operation, say - the extension resolves one from the tester
before `onSetup()` instead. With the check enabled it also resolves one to verify after
`onTearDown()` when the listener already closed the one `onSetup()` retrieved, as the
default listener does. It offers either connection to `connectionRetrieved()` first, so
the listener sees one more retrieval than in 3.5.0, and closes it after the test unless
the tester's listener is `NO_OP_OPERATION_LISTENER`.
Switch such a class to `@DbUnitTest`, or mark its field `@DbUnitTester`, to
opt its parameters in.

*A bare `java.sql.Connection` parameter is never claimed*, so another
extension on the same test that resolves it — Spring's `SpringExtension`,
Testcontainers, a JPA/JDBC harness — does not collide with JUnit's "discovered
multiple competing ParameterResolvers". Inject the `IDatabaseConnection` and
call its `getConnection()` for the JDBC connection.

A `@BeforeEach` parameter resolves before this extension's own setup runs —
JUnit Jupiter always calls `@BeforeEach` methods first — so it sees the
tester/connection exactly as they exist before that setup: the `@DbUnitPrep`
dataset, if any, is not loaded onto it yet, though `@DbUnitProperty` values and the
other `@DbUnitConfig` settings are already in force on it. Ask for the parameter on the
`@Test` method instead when the test needs the already-prepped state.

Not supported on `@AfterEach`, `@AfterAll`, `@BeforeAll`, or a test class
constructor — declined outright rather than resolved. By the time
`@AfterEach` runs, this extension's own `afterTestExecution()` callback has
already closed (or never resolved) the connection it manages, so resolving
one there would hand out an already-closed connection, or leak a
freshly-opened one nothing would ever close. The same timing catches a
direct `databaseTester.getConnection()` call in an `@AfterEach` body: on a
fixed-connection tester it returns the connection this extension just
closed; on a fresh-connection tester (`JdbcDatabaseTester`) it opens one
nothing will close. Do post-test database work in the `@Test` method itself,
or in an `@AfterEach` that fully owns its own connection. The injected
`IDatabaseConnection` is managed for the test's duration and
closed afterward by the driven `PrepAndExpectedTestCase`; do not close it yourself.
That includes a `@BeforeEach` method that fails after receiving it: the test
method and the extension's after-test callback never run then, so the extension
closes the connection in its `afterEach` callback instead.

== When to Use This Instead of Manual Lifecycle Calls

Reach for `DbUnitExtension` when a `@BeforeEach`/`@AfterEach` pair that only
calls `onSetup()`/`onTearDown()` (as shown in link:IDatabaseTester.html[the
IDatabaseTester guide]) would just be boilerplate repeated across every test
class. Write the `@BeforeEach`/`@AfterEach` pair yourself instead when a test
needs other logic around those calls, or targets a JUnit version this
extension doesn't support.
