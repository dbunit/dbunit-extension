= DbUnit Annotations
Jeff Jensen

== Overview

`org.dbunit.annotation` declares the dataset and operation for a test
directly on the class or method, instead of writing `@BeforeEach`/
`@AfterEach` calls or driving link:PrepAndExpectedTestCase.html[PrepAndExpectedTestCase]
by hand. On JUnit 5/6 (Jupiter), add `@DbUnitTest` to register the extension and opt the
class in, also when it declares no other dbUnit annotation:

[source,java]
----
@DbUnitTest
class AccountRepositoryTest
{
    IDatabaseTester databaseTester;

    AccountRepositoryTest() throws ClassNotFoundException
    {
        databaseTester =
                new JdbcDatabaseTester("org.h2.Driver", "jdbc:h2:mem:example;DB_CLOSE_DELAY=-1");
    }

    @Test
    @DbUnitPrep("/dbunit/accounts/prep.xml")
    @DbUnitExpected(value = "/dbunit/accounts/expected.xml", verifyTables = "ACCOUNT")
    @DbUnitTearDownOperation(DbUnitOperation.DELETE_ALL)
    void testWithdraw_sufficientBalance_decrementsBalance()
    {
        // code under test
    }
}
----

These annotations target the *fixed, per-method* case — one test method, one
known dataset, one known expectation. See
<<applicability,When Not to Use These Annotations>> below for the cases they
deliberately do not cover, and what to use instead.

[#glance]
== At a Glance

One pass through the whole vocabulary before the detail below — each row names the section
with its full rules:

[cols="1,3", options="header"]
|===
|Annotation |Use it for

|`@DbUnitTest` |Registers `DbUnitExtension` and opts the class into the annotation-driven lifecycle, also when it declares no other dbUnit annotation — unlike a bare `@ExtendWith(DbUnitExtension.class)`, which keeps the 3.5.0 lifecycle.
|`@DbUnitPrep` |Dataset file(s) to load before the test — see <<prepandsetup>>.
|`@DbUnitSetUpOperation` |The operation to load them with; needed only to replace the tester's own, `CLEAN_INSERT` for dbUnit's built-in testers — see <<prepandsetup>>.
|`@DbUnitExpected` |Dataset file(s) to verify after the test — see <<expected>>.
|`@DbUnitVerifyTable`, `@DbUnitColumnComparer` |Full per-table/per-column verify rules, nested inside `@DbUnitExpected` — see <<expected>>.
|`@DbUnitTearDownOperation` |The cleanup operation to run after the test; defaults to doing nothing — see <<prepandsetup>>.
|`@DbUnitConfig` |Class-level wiring: loader, tester factory, `DatabaseConfig` properties, catalog default, base directory, failure handler — see <<config>>.
|`@DbUnitProperty` |One `DatabaseConfig` name/value pair, nested inside `@DbUnitConfig` — see <<properties>>.
|`@DbUnitTester`, `@DbUnitTestCase` |Field markers injecting an already-built `IDatabaseTester` / `PrepAndExpectedTestCase`, in place of the plain-field auto-scan — see <<resolution>>.
|`@DbUnitRowCountCheck` |Fails the test when a table's row count moved between setup and teardown, catching a table teardown forgot or wrongly cleaned — see <<rowcountcheck>>.
|A catalog class, a composed annotation, or a `DatabaseTesterFactory` implementation |Sharing verify-table definitions, annotation values, or tester construction across many test classes — see <<catalog>>, <<composed>> and <<factories>>.
|===

[#lifecycle]
== The Lifecycle

A test that uses the annotations runs through a
link:PrepAndExpectedTestCase.html[PrepAndExpectedTestCase], whether or not it declares
`@DbUnitExpected`: dbUnit builds a `DefaultPrepAndExpectedTestCase` around the tester for the
test (see `@DbUnitConfig(prepAndExpectedTestCase)`), or drives the `@DbUnitTestCase` instance it
is given.

[cols="1,3", options="header"]
|===
|Step |Behaviour

|Before the test method |`configureTest()` loads the `@DbUnitPrep` and `@DbUnitExpected`
datasets, and `preTest()` sets up the `@DbUnitPrep` dataset with the tester's setup operation, or
the one `@DbUnitSetUpOperation` declares. A test that names no `@DbUnitPrep` file sets up no
data, whatever dataset the tester holds: see <<prepandsetup>>.

|After the test method |`postTest()` compares the database against the `@DbUnitExpected`
dataset, when the test declares one, so the verifying is done for you, then tears down with the
tester's teardown operation, or the one `@DbUnitTearDownOperation` declares, over the prep and
expected datasets. The comparison is skipped when the test method itself already failed, so a
verification failure never masks the real cause.
|===

Without `@DbUnitExpected` the test method asserts results however it likes, or just needs seeded
data; with it, dbUnit's expected-dataset comparison does the verifying.

*The tester is only read.* The test case takes its connection from the tester, and its
operations unless an annotation declares them for the test; its dataset is never read. Nothing
is written to the tester and its listener is not replaced, so
a tester shared through a `static` field or a Spring singleton bean carries nothing from one test
to the next. The tester's own `onSetup()` and `onTearDown()` do not run, so an override of either in
a tester subclass has no effect on such a test, and its listener is told about the shared
connection through `connectionRetrieved()` when the test case acquires it, before the row count
baseline or anything else reads the connection's configuration, and again before each set up and
tear down operation, but never `operationSetUpFinished()` or `operationTearDownFinished()`: the
test case decides when its connection closes, see <<connection-ownership>>.

*A test that uses none of the annotations keeps the 3.5.0 lifecycle:* a bare
`@ExtendWith(DbUnitExtension.class)` class with one plain, unannotated `IDatabaseTester` field.
`@DbUnitTest` is not "none of the annotations": it opts the class in, also when nothing else is
declared.
The extension then calls the tester's `onSetup()` and `onTearDown()` and runs the row count check
around them, as before — see link:DbUnitExtension.html[DbUnitExtension].

dbUnit configures only `DefaultPrepAndExpectedTestCase` and its subclasses. A hand-written
`PrepAndExpectedTestCase` is driven as it is — see <<othertestcase>>.

Every annotated test runs the same tester/test-case resolution below and honors `@DbUnitConfig`.

[#resolution]
== Resolving the Tester or Test Case

First match wins:

[cols="1,4", options="header"]
|===
|Order |Source

|1 |A field annotated `@DbUnitTestCase`, whose type implements
`PrepAndExpectedTestCase` — that instance is driven directly; the extension
constructs nothing. The "the object already exists, inject it" case.

|2 |A field annotated `@DbUnitTester`, whose type implements
`IDatabaseTester`.

|3 |`@DbUnitConfig(databaseTesterFactory = ...)` — the named
`DatabaseTesterFactory` is instantiated and asked for a tester
(<<factories>>). Needed because `IDatabaseTester` implementations have no
uniform no-arg constructor (`JdbcDatabaseTester` needs a driver and URL,
`DataSourceDatabaseTester` a `DataSource`, `JndiDatabaseTester` a lookup
name).

|4 |The original (3.5.0) field auto-scan: exactly one non-static field
assignable to `IDatabaseTester`, nearest declaring class wins. Unchanged, so
every 3.5.0 test keeps working untouched.
|===

Field discovery walks every test instance in scope, innermost first, so a
`@Nested` test class inherits its enclosing class's tester field - or
shadows it outright with a field of its own, the same marker or not, the
same way a `@Nested` class's own unmarked `IDatabaseTester` field already
shadows an enclosing one. Ambiguity is only ever rejected with
`IllegalStateException` *within* one test instance's own class hierarchy:
two fields with the same marker there, or both a `@DbUnitTester` and a
`@DbUnitTestCase` field declared on that same instance.

A `@DbUnitTestCase` field resolving tier 1 supplies the tester too, when it is a
`DefaultPrepAndExpectedTestCase`: its own, which it must already have, as dbUnit uses
the instance as its owner built it (<<injected-testcase-config>>). An instance without a tester
is rejected with an `IllegalStateException` that says to give it one where it is built, and
tiers 2 to 4 and `databaseTesterFactory` are not consulted for it. A `@DbUnitTester` field is not
a substitute for a tester: it is rejected outright alongside `@DbUnitTestCase` (see above). Any
other `PrepAndExpectedTestCase` implementation tells dbUnit of no tester, and needs none - see
<<othertestcase>>.

[#othertestcase]
=== A Test Case That Is Not a DefaultPrepAndExpectedTestCase

A `@DbUnitTestCase` field whose type implements `PrepAndExpectedTestCase` but is
not a `DefaultPrepAndExpectedTestCase` - for example a class that wraps its own tester
and connection - is driven as it is. dbUnit gives it the test's files
(`@DbUnitPrep`, `@DbUnitExpected`) and calls `configureTest()`, `preTest()` and
`postTest()`. It knows no tester and no connection of it, so everything that needs one
is rejected before any database work, with one `IllegalStateException` that names it,
when the test declares it:

* `@DbUnitSetUpOperation`, `@DbUnitTearDownOperation` and `@DbUnitRowCountCheck`;
* the `@DbUnitConfig` attributes `dataFileLoader`, `failureHandler`,
  `properties`, `databaseTesterFactory` and `prepAndExpectedTestCase`; and
* an `IDatabaseTester` or `IDatabaseConnection` test method parameter.

Configure such a test case where it is built instead. The rest works as for any other
test case, including the tables to verify: a `@DbUnitExpected` that names none verifies
every table of the expected datasets, read with the `@DbUnitConfig` loader, with the rules of
the `@DbUnitConfig(verifyDefinitions)` catalog for the tables it defines.

`@DbUnitTester` and `@DbUnitTestCase` both accept a `static` field, the way a
tester or test case shared across every method in a class is typically
declared:

[source,java]
----
@DbUnitTest
class AccountRepositoryTest
{
    @DbUnitTester
    static final IDatabaseTester databaseTester;

    static
    {
        try
        {
            databaseTester =
                    new JdbcDatabaseTester("org.h2.Driver", "jdbc:h2:mem:example;DB_CLOSE_DELAY=-1");
        }
        catch (ClassNotFoundException e)
        {
            throw new ExceptionInInitializerError(e);
        }
    }

    @Test
    @DbUnitPrep("/dbunit/accounts/prep.xml")
    void testFindAll() { ... }
}
----

*A `static` field is one instance shared by every test method in the class.* A tester is
only read, so a `static` `@DbUnitTester` is shared safely, also under parallel execution
(`junit.jupiter.execution.parallel.enabled=true` with per-class or per-method concurrency), as
long as it hands out a connection of its own on each call; a tester over one fixed connection
shares that connection among the concurrent test methods. A `static` `@DbUnitTestCase`, or any
`@DbUnitTestCase` instance field under `@TestInstance(Lifecycle.PER_CLASS)`, holds the datasets
and the connection of one test at a time, so concurrent test methods would race each other, as
dbUnit drives it without synchronization. Keep a class sharing such a field, or a tester over one
fixed connection, running sequentially (JUnit Jupiter's own default), or give each test method its
own non-shared field instead.

[#prepandsetup]
== @DbUnitPrep and @DbUnitSetUpOperation

`DbUnitOperation` has eight values, each mapping to the corresponding
`DatabaseOperation` constant:

[cols="1,3", options="header"]
|===
|Value |Meaning

|`CLEAN_INSERT` |Deletes all rows then inserts the dataset rows. The
default `@DbUnitSetUpOperation` operation.
|`INSERT` |Inserts dataset rows. Fails if a row already exists.
|`UPDATE` |Updates existing rows in the dataset.
|`REFRESH` |Inserts or updates rows (upsert).
|`DELETE` |Deletes rows matching the dataset.
|`DELETE_ALL` |Deletes all rows from each table in the dataset.
|`TRUNCATE_TABLE` |Truncates each table in the dataset.
|`NONE` |Performs no operation. The default `@DbUnitTearDownOperation` operation.
|===

Data and operation are deliberately separate annotations rather than one
fused annotation:

[cols="1,2,2", options="header"]
|===
| |Before the test |After the test

|*Data* |`@DbUnitPrep(files)` |`@DbUnitExpected(files, ...)`
|*Operation* |`@DbUnitSetUpOperation(operation)` |`@DbUnitTearDownOperation(operation)`
|===

The split matters because a method-level annotation overrides a class-level
one *wholesale* — attributes do not merge (`@DbUnitConfig` is the one exception, see <<config>>). Fused, a class-level operation
would be silently lost the moment a method declared its own files. Split,
the two resolve independently:

[source,java]
----
@DbUnitTest
@DbUnitSetUpOperation(DbUnitOperation.REFRESH)   // class-wide, set once
@DbUnitTearDownOperation(DbUnitOperation.DELETE_ALL)
class AccountRepositoryTest
{
    IDatabaseTester databaseTester;

    AccountRepositoryTest() throws ClassNotFoundException
    {
        databaseTester =
                new JdbcDatabaseTester("org.h2.Driver", "jdbc:h2:mem:example;DB_CLOSE_DELAY=-1");
    }

    @Test
    @DbUnitPrep("a.xml")   // still uses REFRESH
    void testOne() { ... }

    @Test
    @DbUnitPrep("b.xml")   // still uses REFRESH
    void testTwo() { ... }
}
----

Because dbUnit's built-in testers already default to `CLEAN_INSERT`, the common case is a
single annotation — `@DbUnitPrep("accounts.xml")` alone names only the dataset and runs the
tester's own setup operation. `@DbUnitSetUpOperation` with no `@DbUnitPrep` at all
is valid, but the operation runs over no data: no dataset is loaded from files and the
dataset a tester holds is never read. A bare `@DbUnitSetUpOperation` resolves to
`CLEAN_INSERT`, not `NONE`, so `@DbUnitSetUpOperation` with no `@DbUnitPrep` logs a `WARN`,
as the operation has nothing to act on.

`@DbUnitPrep` takes several files, which are combined into one dataset; tables of the same
name merge into one. Names are matched ignoring case unless the test's connection has
`FEATURE_CASE_SENSITIVE_TABLE_NAMES` on, set for example with a `@DbUnitProperty`, as
`DefaultPrepAndExpectedTestCase` does for its own prep files.

The tester's own setup and teardown operations are used —
preserving a `@BeforeEach` method's own `setSetUpOperation()`/`setTearDownOperation()`,
including an operation `DbUnitOperation` cannot express, such as MSSQL's
`InsertIdentityOperation.CLEAN_INSERT` or a `TransactionOperation` — except where an annotation
replaces them for the test: `@DbUnitSetUpOperation` replaces the setup operation and
`@DbUnitTearDownOperation` the teardown operation. The dataset is never the tester's: it is the
files `@DbUnitPrep` names, and a test that names none sets up no data. `@DbUnitPrep` names only
the dataset. So `@DbUnitPrep("a.xml")` alone runs `REFRESH` on
a tester already set to `REFRESH`, and `CLEAN_INSERT` on a built-in tester nobody changed;
declare `@DbUnitSetUpOperation(DbUnitOperation.CLEAN_INSERT)` alongside it to run that on the
former. A replacement is the operation of the test case that runs this test, never
written to the tester, and lasts for that test only. The test case sets up and cleans up with
the `@DbUnitPrep` and `@DbUnitExpected` datasets, the teardown operation running over both, with or
without `@DbUnitExpected`. An
injected `@DbUnitTestCase` is the exception: it runs with its tester's operations as its owner set
them and takes its datasets from the files the test names, so neither operation annotation
replaces them, and declaring either next to it is rejected - see <<injected-testcase-config>>.

*Migrating a `@BeforeEach` dataset.* A 3.5.0-style test that gives the tester its dataset with
`setDataSet()` in a `@BeforeEach` method keeps working while it uses none of these annotations:
the extension then runs the tester's own `onSetup()` and `onTearDown()`, dataset included, as
before - see link:DbUnitExtension.html[DbUnitExtension]. Once the test uses an annotation, such as
`@DbUnitExpected` or `@DbUnitRowCountCheck`, the dataset is not read and dbUnit logs a `WARN` that
says so: move the dataset into a file and name it with `@DbUnitPrep`. A dataset that has to be
built in code stays with the 3.5.0 lifecycle, or with the programmatic
link:PrepAndExpectedTestCase.html[PrepAndExpectedTestCase] API.

*Nothing bleeds between test methods.* Each method's resolved annotations —
its own, plus any inherited from its class or a parent class — fully
determine what gets applied for that method. The tester is never written, so a `static`
`@DbUnitTester` field (or any tester under `@TestInstance(PER_CLASS)`, or a Spring singleton bean)
never carries one method's `@DbUnitPrep`/`@DbUnitSetUpOperation`/`@DbUnitTearDownOperation` onto
the next, and a `@BeforeEach` operation, being re-set every method, is read as it is. The
same holds for `@DbUnitProperty`
values on a connection that outlives the test, such as a fixed connection handed
to the tester, one a `CachingConnectionProvider` caches, or one its tester's listener leaves
open: they are put back when the test ends — see <<properties>>.

`@DbUnitTearDownOperation` is the counterpart of `@DbUnitSetUpOperation`, defaulting to
`DbUnitOperation.NONE`. It has no data annotation of its own: the dataset
already prepared (prep, plus expected when there is one) is what the
operation runs against. To tear down an extra table, list it — empty — in
the prep dataset instead.

[#expected]
== @DbUnitExpected, @DbUnitVerifyTable, @DbUnitColumnComparer

`@DbUnitExpected` names the expected dataset file(s) to verify after the test.
Valid with no `@DbUnitPrep` at all — the
database state already present is what gets verified. The expected dataset
must always be named, with `value`: the tables verified are
compared to it, so the forms below only choose which of its tables are
compared, and an annotation naming no dataset fails fast, whatever else it
declares, instead of failing at the end of the test with an obscure error.

Which tables to verify, and with what rules, comes in three forms so the common cases
stay short. The expected dataset, or `verifyTables` when given, decides which tables are
verified; a class-level `@DbUnitConfig(verifyDefinitions)` catalog only supplies each table's
rules (see <<catalog,the catalog section>> below):

[cols="1,3", options="header"]
|===
|Written |Meaning

|nothing |Verify every table in the expected dataset. A table the catalog defines is
verified with the catalog's definition, any other with the default rules; a catalog table the
expected dataset lacks is not verified. The tables are read with the same data file loader that
later compares the dataset: an injected `@DbUnitTestCase` instance's own loader.

|`verifyTables = {"ACCOUNT", "TXN"}` |Verify exactly these tables, each with its
definition from the catalog when it has one and the default rules when not — which also avoids
repeating a bare `@DbUnitVerifyTable` per table just to name them.

|`verify = @DbUnitVerifyTable(...)` |Full per-table rules, inline: column
include/exclude, comparers, sort mode.
|===

`verify` together with `verifyTables` is rejected as ambiguous: `verify` declares the rules
of its tables, `verifyTables` takes them from a catalog.

Setting `verify` together with `verifyTables` fails fast rather
than silently picking one:

[source,java]
----
@DbUnitExpected(value = "expected.xml",
        verifyTables = "ACCOUNT", // IllegalStateException: ambiguous with verify() below
        verify = @DbUnitVerifyTable("ACCOUNT"))
void testAmbiguous() { ... } // never runs - rejected before the test executes
----

A worked example combining a prep file, an expected file, and per-table
rules:

[source,java]
----
@Test
@DbUnitPrep("/dbunit/accounts/prep.xml")
@DbUnitExpected(value = "/dbunit/accounts/expected.xml",
        verify = @DbUnitVerifyTable(value = "ACCOUNT",
                exclude = "CREATED_TS",
                columnComparers = @DbUnitColumnComparer(column = "BALANCE",
                        comparer = IsActualGreaterThanExpectedValueComparer.class)))
@DbUnitTearDownOperation(DbUnitOperation.DELETE_ALL)
void testWithdraw_sufficientBalance_decrementsBalance() { ... }
----

`@DbUnitColumnComparer.comparer()` and `@DbUnitVerifyTable.defaultComparer()`
are reflectively instantiated with their no-arg constructor. That reaches
any custom `ValueComparer`, and the stateless `ValueComparers` constants —
those whose implementation class has a no-arg constructor. It does *not*
reach a `ValueComparers` constant that is a configured instance built with
constructor arguments — the timestamp-tolerance comparers, for example
`isActualWithinOneMinuteNewerOfExpectedTimestamp`; naming one of those here
fails fast with an `IllegalStateException` naming the two ways to use one. Either
declare it as a `VerifyTableDefinition` constant in <<catalog,a catalog class>>,
or name a subclass whose public no-arg constructor passes the arguments on, which
works inline:

[source,java]
----
public class WithinOneMinuteNewer
        extends IsActualWithinToleranceOfExpectedTimestampValueComparer
{
    public WithinOneMinuteNewer()
    {
        super(0, 60_000);
    }
}
----

Each comparer class is instantiated once for the whole run and shared by every test that names
it, in whatever order the tests run, so a custom comparer must be stateless: it keeps nothing
between calls and depends on no mutable external state.

An empty `include()` (the default) includes every column, as a `null` or empty include
array does for a `VerifyTableDefinition`; an annotation cannot express `null`.

[#catalog]
== The Shared VerifyTableDefinition Catalog

One fixed table set for every test is not how real suites actually verify
data — they keep one shared class holding a `VerifyTableDefinition` constant
per table, and each test verifies a different subset. `@DbUnitConfig(verifyDefinitions)` names one
or more **catalog classes**. The catalog supplies the rules of each table; the expected dataset, or
`verifyTables`, decides which tables are verified:

[source,java]
----
public class AppVerifyTables
{
    public static final VerifyTableDefinition ACCOUNT =
            new VerifyTableDefinition("ACCOUNT", new String[] {"ID", "CREATED_TS"});
    public static final VerifyTableDefinition TRANSACTION =
            new VerifyTableDefinition("TRANSACTION", new String[] {"ID"},
                    ValueComparers.isActualEqualToExpected,
                    new ColumnValueComparerMapBuilder()
                            .add("POSTED_TS", ValueComparers.isActualWithinOneMinuteNewerOfExpectedTimestamp)
                            .build());
    public static final VerifyTableDefinition CUSTOMER =
            new VerifyTableDefinition("CUSTOMER", new String[] {"UPDATED_TS"});
}
----

[source,java]
----
@DbUnitTest
@DbUnitConfig(verifyDefinitions = AppVerifyTables.class)
@DbUnitTearDownOperation(DbUnitOperation.DELETE_ALL)
class AccountRepositoryTest
{
    IDatabaseTester databaseTester;

    AccountRepositoryTest() throws ClassNotFoundException
    {
        databaseTester =
                new JdbcDatabaseTester("org.h2.Driver", "jdbc:h2:mem:example;DB_CLOSE_DELAY=-1");
    }

    @Test
    @DbUnitPrep("accounts-prep.xml")
    @DbUnitExpected(value = "accounts-expected.xml",
            verifyTables = {"ACCOUNT", "TRANSACTION"})
    void testWithdraw_sufficientBalance_decrementsBalance() { }

    @Test
    @DbUnitPrep("accounts-prep.xml")
    @DbUnitExpected(value = "customers-expected.xml",
            verifyTables = {"CUSTOMER"})
    void testRename_existingCustomer_updatesName() { }

    @Test
    @DbUnitPrep("accounts-prep.xml")
    @DbUnitExpected("full-expected.xml")
    void testFullRefresh_noVerifyAttributeAtAll_verifiesEveryTableOfTheExpectedDataset() { }
}
----

The third method sets neither `verify` nor `verifyTables`, so every table of
`full-expected.xml` is verified: `ACCOUNT`, `TRANSACTION` and `CUSTOMER` with the
definitions `AppVerifyTables` holds for them, and a table the catalog does not define, such as
`AUDIT`, with the default rules. A catalog table that `full-expected.xml` does not contain is not
verified, and a table `verifyTables` names that the catalog lacks is verified with the default
rules too.

The catalog is a *plain constants class* — no interface, no boilerplate,
nothing to keep in sync. This is deliberately the same shape
link:PrepAndExpectedTestCase.html#common_classes_for_examples[PrepAndExpectedTestCase]
already teaches with its `TableNames`/`ColumnNames`/`AppValueComparers`/
`VerifyTableDefinitions` helper classes, so an existing project's constants
work here unchanged.

The definitions are shared, too: every test naming the same catalog classes gets the same
`VerifyTableDefinition` objects for the whole run. A test must never change them - their setters, such as
`setSortOnFilteredColumnsOnly()`, included - and a comparer or verifier inside one must be
stateless, or a later test's result depends on the order the tests ran in.

`verifyDefinitions` is an attribute of `@DbUnitConfig` only, so the catalogs are
set once for a class or a composed annotation, and a method chooses with `verify` or
`verifyTables`. A catalog class has its
`public static final VerifyTableDefinition` fields read directly. The same
table name defined in two catalog classes named together is rejected rather
than silently resolved by declaration order. Table names are compared ignoring
case, as dbUnit finds a table in a dataset: `verifyTables = "account"` selects
a catalog's `ACCOUNT` definition, and `ACCOUNT` in one catalog class and
`account` in another are the same table. The same goes for `verifyTables` and
`verify` entries naming one table twice. A schema that holds tables whose names
differ only in case, with `FEATURE_CASE_SENSITIVE_TABLE_NAMES` on, cannot name
more than one of them in a single verification spec.

[#factories]
== Sharing Values and Factory Classes

A Java annotation cannot reference a `String[]`, a `Properties` or a `VerifyTableDefinition`
constant, so a value that many test classes share is written once in a composed annotation
(<<composed>>): a project annotation carrying `@DbUnitPrep({"/dbunit/accounts/prep.xml"})`
shares the paths, one carrying `@DbUnitConfig(properties = ...)` shares the properties, and
`verifyDefinitions` names a catalog class that holds the `VerifyTableDefinition` constants
(<<catalog>>). Write the paths of a composed annotation as absolute ones: a relative path
resolves against the class that carries the composed annotation.

One attribute takes a class because the value it supplies is code:
`@DbUnitConfig(databaseTesterFactory = ...)` names a `DatabaseTesterFactory`, which is
instantiated once through its own `public` no-arg constructor and asked for the tester with
`getDatabaseTester()`. `IDatabaseTester` implementations have no uniform no-arg constructor
(`JdbcDatabaseTester` needs a driver and URL, `DataSourceDatabaseTester` a `DataSource`,
`JndiDatabaseTester` a lookup name), so the factory builds one. A missing or throwing
constructor fails fast with an `IllegalStateException` naming the attribute, and a factory
returning `null` is rejected.

[#config]
== @DbUnitConfig

Class-level wiring, carried automatically two separate ways: `@Inherited`, so
a subclass of a project base class gets it too; and, independently, via
composed-annotation lookup (<<composed>>), so a project's own annotation
carrying `@DbUnitConfig` as a meta-annotation is found the same as a
directly-declared one - a different mechanism from `@Inherited`, not a
consequence of it:

Next to a `@DbUnitTestCase` field, the attributes that would configure that instance are
rejected: it is used as its owner built it - see <<injected-testcase-config>>.

[cols="1,3", options="header"]
|===
|Attribute |Purpose

|`dataFileLoader` |The `DataFileLoader` used for every dataset file.
Defaults to
link:../apidocs/org/dbunit/util/fileloader/FileExtensionDataFileLoader.html[FileExtensionDataFileLoader],
which dispatches by extension — see link:../datasets/fileloader.html[Data File Loader]. A loader
of that default or of any other class that does not cache is built for each test, so a test case
that changes the loader it is given, such as by adding replacement objects, changes no other
test's. One instance of a `CachingDataFileLoader` class is built and shared by the tests of its
scope instead: all the tests of the run under JUnit Jupiter, those of one test class under
Spring. A value its constructor computes, such as a replacement of the current time, is then
computed once for the scope, and the loader must be safe for tests that run in parallel. Use
`CachingFileExtensionDataFileLoader` to load each file once for the scope instead of once per
test — see link:../datasets/fileloader.html#caching[Caching Parsed Datasets].

|`databaseTesterFactory` |See <<resolution,resolution order>> tier 3.

|`prepAndExpectedTestCase` |The `PrepAndExpectedTestCase` implementation to
construct to run the test when no `@DbUnitTestCase` field
supplies one, via a `(DataFileLoader, IDatabaseTester)`
constructor — the same shape `DefaultPrepAndExpectedTestCase` itself has.
Defaults to `DefaultPrepAndExpectedTestCase`. In practice this means a
`DefaultPrepAndExpectedTestCase` *subclass* (to override a hook such as
`setUpDatabaseConfig()`): a from-scratch `PrepAndExpectedTestCase` would
have to reimplement dataset loading, comparison, and cleanup — see
<<injected-testcase-config>>.

|`properties` |`DatabaseConfig` properties to apply — see <<properties>> below.

|`verifyDefinitions` |The catalog classes that supply the rules of the tables a test verifies — see <<catalog>>.

|`dataSetBaseDir` |A classpath directory prefix — see <<paths>> below.

|`failureHandler` |A `FailureHandler` for verification failures, in place of
dbUnit's own default.
|===

*Declarations merge attribute by attribute.* A test can be in scope of several `@DbUnitConfig`
declarations at once: on its class, on its superclasses, on the annotations composed into any
of them (<<composed>>), and on the enclosing classes of a `@Nested` one. For each attribute the
nearest declaration that sets it wins, so a subclass that declares only `failureHandler` keeps
the `dataFileLoader` and the `properties` of its base class. An attribute is set when it differs
from its default, so a nearer declaration can override an inherited value by naming the one it
wants, for example `dataFileLoader = FileExtensionDataFileLoader.class`, but it cannot clear an
inherited one. The `verifyDefinitions` array is taken whole from the nearest declaration that sets
it, never combined with a farther one's. The `properties` are merged by property name instead: a
nearer declaration overrides a property of a farther one by naming it again, in its long or its
short form, and the farther one's other properties still apply. A nearer declaration can set a
property back to its default by naming it. Every other annotation in this family is replaced
whole by the nearer declaration.

[#connection-ownership]
=== Who Closes the Connection

dbUnit closes the connection the test case sets up, verifies and cleans up on — which the row
count check and an `IDatabaseConnection` parameter share — when the test is over, unless it
belongs to someone else.
The one signal for that is set on the tester, once, where it is built, so every test that uses
the tester gets it right: an `IOperationListener` that is `NO_OP_OPERATION_LISTENER` itself says
its connections are managed elsewhere, as it did in the 3.5.0 lifecycle. A listener that wraps
it, such as a decorator of your own, does not say so. An injected
`@DbUnitTestCase` instance built with `setCloseConnectionAfterTest(false)` keeps its connection
open too. A tester that is not given the no-op listener only costs a new
connection per test when it shares a `CachingConnectionProvider`, which replaces a closed
connection.

Leaving the connection open requires a tester that hands out the same connection on repeated
calls, as one over a `CachingConnectionProvider` or over one fixed connection does. With a
tester that hands out a new one each time, such as a `JdbcDatabaseTester` without a
`CachingConnectionProvider` or a `DataSourceDatabaseTester` over a connection pool, nothing
closes the connection left open, so each test leaves one open, except that an injected test
case reused across tests keeps one. A step that fails also makes the
test case forget its connection so that the next step acquires another, and the forgotten one
stays open with nothing referencing it. dbUnit logs a warning when it sees a connection left
open with a `JdbcDatabaseTester` that has no `CachingConnectionProvider`. A connection dbUnit
closes while its autocommit is off has its open transaction rolled back first: Derby and DB2
refuse to close one, and Oracle commits it on close, as the 3.5.x extension's close did,
so on Oracle the prep and teardown writes of such a connection are now discarded, not
committed - see link:../connections.html[Connections].

[#injected-testcase-config]
=== @DbUnitConfig and an injected @DbUnitTestCase

An injected `@DbUnitTestCase` instance is used as its owner built it. dbUnit gives it the
test's files (`@DbUnitPrep`, `@DbUnitExpected`) and calls `configureTest()`, `preTest()` and
`postTest()`; for a `DefaultPrepAndExpectedTestCase` or a subclass it also applies
`@DbUnitRowCountCheck`, through `setRowCountCheckOverride()`, and puts back the override the
instance had when the test ends, so a `static` field never carries one method's override onto the
next. Nothing else is
configured: the data file loader, failure handler, `DatabaseConfig` properties,
`closeConnectionAfterTest`, and the tester with its setup and teardown operations belong to the
instance, and are set where it is built.

A test that declares anything that would configure the instance is therefore rejected before
any database work, with one `IllegalStateException` that names it and says to configure the
instance where it is built: `@DbUnitSetUpOperation`, `@DbUnitTearDownOperation`, and the
`@DbUnitConfig` attributes `dataFileLoader`, `failureHandler`, `properties`,
`databaseTesterFactory` and `prepAndExpectedTestCase`. An instance
without a tester is rejected too, when it is resolved, and so is one without a data file
loader when the test runs, which a `@BeforeEach` method may still give it: its
`configureTest()`, which dbUnit calls for every test, needs the loader even when the test names
no dataset file. Any other `PrepAndExpectedTestCase` implementation is rejected for more - see
<<othertestcase>>.

[source,java]
----
@DbUnitTestCase
static final DefaultPrepAndExpectedTestCase testCase = newTestCase();

private static DefaultPrepAndExpectedTestCase newTestCase()
{
    IDatabaseTester tester;
    try
    {
        tester = new JdbcDatabaseTester(...);
    }
    catch (ClassNotFoundException e)
    {
        throw new IllegalStateException(e);
    }
    tester.setTearDownOperation(DatabaseOperation.DELETE_ALL);
    DefaultPrepAndExpectedTestCase testCase =
            new DefaultPrepAndExpectedTestCase(new FlatXmlDataFileLoader(), tester, true);
    testCase.setFailureHandler(new DiffCollectingFailureHandler());
    return testCase;
}
----

[#properties]
=== DatabaseConfig Properties

`@DbUnitProperty` entries are collected into a `Properties` instance and
handed to `DatabaseConfig.setPropertiesByString(Properties)`, which accepts
both the long `http://www.dbunit.org/...` names and their short forms, the last
part of a long name, such as `batchSize`, or several whole last parts, such as
`mssql/identityColumnFilter`. Only the end of a part, such as `Size`, is no
property name and is rejected:

[source,java]
----
@DbUnitConfig(properties = {
        @DbUnitProperty(name = "caseSensitiveTableNames", value = "true"),
        @DbUnitProperty(name = "batchSize", value = "50")
})
----

A property may be given once, in either form: `batchSize` and
`http://www.dbunit.org/properties/batchSize` name the same property, so
declaring both is rejected, since which value
won would depend on the order a `Properties` happens to be iterated in. Every
name is passed on in its long form.

Named members are used instead of a `String[]` of `"name=value"` pairs so
each entry is self-documenting, IDE-completable, and cannot be broken by a
value that itself contains `=` (an escape pattern, for instance). For
properties shared across several test classes, put them in a composed
annotation (<<factories>>).

*Which connection the properties reach.* The test case applies `@DbUnitProperty` values
directly to the connection it resolves for
`configureTest()`/`setupData()`/`verifyData()`/`cleanupData()`, which is also the one an
`IDatabaseConnection` parameter is given, so the setup and teardown operations do not matter, and
nothing goes through the tester's `IOperationListener` to do it. A connection the test method
retrieves from the tester itself does not get them. The test case tells the tester's own listener's
`connectionRetrieved()` about the shared connection when it acquires it and again before each set
up and tear down operation, always before applying these values, so they win over what that
listener sets. An injected
`@DbUnitTestCase` takes its properties from where it is built, through
`setDatabaseConfigProperties()`: declaring them next to it is rejected - see
<<injected-testcase-config>>.

`DefaultPrepAndExpectedTestCase` applies
`@DbUnitProperty` values through its `setUpDatabaseConfig(DatabaseConfig)`
hook. *A subclass that overrides `setUpDatabaseConfig()` — the pre-3.6.0 way to
configure a `DatabaseConfig` — must call `super.setUpDatabaseConfig(config)`*,
or the `@DbUnitProperty` values are silently dropped. The extension logs a
warning when it detects such an override alongside `properties`,
since it cannot tell from reflection whether the `super` call is there. Either
add the `super` call, or drop `@DbUnitProperty` and configure the
`DatabaseConfig` entirely in the override.

*The values last for the test.* A `DatabaseConfig` belongs to its connection, so
a connection that outlives the test — a fixed connection handed to the tester,
one a `CachingConnectionProvider` caches, or one its tester's listener leaves open
(<<connection-ownership>>) — would otherwise carry one test's
`@DbUnitProperty` values into whichever test uses it next. When the test ends,
each value is put back to what it replaced: the default, or what the tester's own
`IOperationListener#connectionRetrieved()` or a `@BeforeEach` set before the
values were applied. Values set on the `DatabaseConfig` by other means during the
test, including a different value for the same property, are overwritten by that
put-back. A connection the test closes after it needs none of this; the put-back
on it is harmless.

[#rowcountcheck]
== @DbUnitRowCountCheck

`@DbUnitRowCountCheck` turns on the
link:../components/rowcountcheck.html[row count check] for a class or method: it snapshots
every table's row count *before* `@DbUnitPrep` loads, snapshots again after teardown, and
fails the test by name when any count moved — catching a table the test forgot to list for
teardown (whose rows survive and break a *later* test) and equally a reference table it
wrongly listed (whose count went *down*).

Because the baseline is taken before `@DbUnitPrep`, a passing check means teardown
returned the database to its *pre-prep* state — the prep data removed too, not just the
test's own writes. `@DbUnitRowCountCheck` with `@DbUnitPrep` and no `@DbUnitTearDownOperation` (the
`NONE` default) therefore *fails*: the prep rows are still there. Pair it with
`@DbUnitTearDownOperation(DbUnitOperation.DELETE_ALL)`, as the example below does.

[source,java]
----
@DbUnitTest
@DbUnitRowCountCheck
class AccountRepositoryTest
{
    IDatabaseTester databaseTester = new JdbcDatabaseTester(...);

    @Test
    @DbUnitPrep("accounts-prep.xml")
    @DbUnitTearDownOperation(DbUnitOperation.DELETE_ALL)
    void testWithdraw_sufficientBalance_decrementsBalance() { ... }
}
----

`enabled()` defaults to `true`, so the bare annotation means "on"; it exists for the
override direction — a class-level check with one method that legitimately leaves rows
behind (a test asserting that an audit trail *persists*, say) writes
`@DbUnitRowCountCheck(enabled = false)` on that method rather than losing the check for the
whole class.

Five sources can speak, highest priority first:

[cols="1,3", options="header"]
|===
|Order |Source

|1 |The `-Ddbunit.rowCountCheck=false` system property — force-disables the check locally
without editing code.

|2 |`@DbUnitRowCountCheck` — method level, else class level. An `enabled = false` stays an
opt-out when a CI run force-enables the check.

|3 |The `-Ddbunit.rowCountCheck` system property set to `true`, or present with no value —
force-enables the check across a CI run for every test that declares nothing.

|4 |`DatabaseConfig.FEATURE_ROW_COUNT_CHECK`.

|5 |Default `false`.
|===

Four behaviours worth knowing explicitly, because each is a place a reader would otherwise
guess wrong:

* A method-level `@DbUnitRowCountCheck` overrides a class-level one *wholesale* —
  `exclude()` included, the same rule as everywhere else in this family. A method that
  wants one extra exclusion has to repeat the class-level ones; they are not merged.
* The `-Ddbunit.rowCountCheckExcludeTables` system property *adds* its patterns to `exclude()`
  and never replaces them, so a suite-wide list does not re-enable the check for the tables a
  test excluded.
* The check compares *row counts*, not row contents — an `UPDATE` that changes a value
  without changing how many rows are present passes. It catches a leaked or wrongly
  removed row, not a data mismatch; that is what `@DbUnitExpected` verification is for.
* This annotation drives the check through the test case — an injected
  `DefaultPrepAndExpectedTestCase` takes it through its override methods, and any other
  injected implementation rejects it, see <<othertestcase>>.

[#composed]
== Reusing a Whole Configuration: Composed Annotations

For configuration shared across many test classes, compose one project
annotation carrying `@DbUnitTest` alongside `@DbUnitConfig` and the
lifecycle annotations. This works for free — annotation lookup finds
composed (meta-)annotations, not just directly-declared ones:

[source,java]
----
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@Inherited
@DbUnitTest
@DbUnitConfig(dataFileLoader = FlatXmlDataFileLoader.class,
        properties = @DbUnitProperty(name = "caseSensitiveTableNames", value = "true"))
@DbUnitSetUpOperation(DbUnitOperation.REFRESH)
public @interface AppDatabaseTest {}
----

Every test class then carries a single `@AppDatabaseTest`. Its `@DbUnitConfig` merges, attribute
by attribute, with the one a class declares itself and with a base class's (<<config>>), so a
class adding `@DbUnitConfig(failureHandler = ...)` keeps the loader and the properties it
composes, and one adding a `@DbUnitProperty` of its own keeps the properties it composes apart
from the one it names again. The same works for a shared
dataset: a composed annotation carrying `@DbUnitPrep("/dbunit/accounts/prep.xml")` gives each
test class carrying it that prep file. Write such a path as an absolute one, as a relative
path resolves against the class that carries the composed annotation (<<paths>>).

[#paths]
== Dataset Path Resolution

Every `@DbUnitPrep`/`@DbUnitExpected` path resolves to an absolute classpath
resource in this order:

[cols="1,3", options="header"]
|===
|Order |Rule

|1 |A path already starting with `/` — used as-is. Always wins, so a shared
file outside the base directory stays reachable.

|2 |`@DbUnitConfig(dataSetBaseDir = "...")`, when set — prefixed to the
path.

|3 |Otherwise — resolved relative to the package of the class that declares the
annotation, matching the convention
link:PrepAndExpectedTestCase.html[PrepAndExpectedTestCase] already teaches. That is the
test class itself, unless the annotation is inherited from a base class, or sits on an
inherited test method, in another package: the path then names a file next to that base
class.
|===

`dataSetBaseDir` exists because the dominant real-world idiom is a shared
directory constant concatenated onto every file name:

[source,java]
----
@DbUnitTest
@DbUnitConfig(dataSetBaseDir = "/dbunit/accounts/")
class AccountRepositoryTest
{
    IDatabaseTester databaseTester;

    AccountRepositoryTest() throws ClassNotFoundException
    {
        databaseTester =
                new JdbcDatabaseTester("org.h2.Driver", "jdbc:h2:mem:example;DB_CLOSE_DELAY=-1");
    }

    @Test
    @DbUnitPrep("accounts-prep.xml")
    @DbUnitExpected("accounts-expected.xml")
    @DbUnitTearDownOperation(DbUnitOperation.DELETE_ALL)
    void testWithdraw_sufficientBalance_decrementsBalance() { }
}
----

The dataset format is inferred from the file extension by the configured
`dataFileLoader` — see link:../datasets/fileloader.html[Data File Loader]
for the extension table and for using a directory-based format (CSV) or
full (non-flat) XML instead.

[#applicability]
== When Not to Use These Annotations

We cannot write every dbUnit test with annotations.

*You want dbUnit to seed data but verify results your own way.* That is not
a gap — it is the <<lifecycle,lifecycle without @DbUnitExpected>>. Use `@DbUnitPrep`/
`@DbUnitSetUpOperation`/`@DbUnitTearDownOperation` with no `@DbUnitExpected`, and assert in the
test method with whatever tooling you already have. `@DbUnitExpected` exists
only for the case where you want dbUnit's expected-dataset comparison to do
the verifying; there is no annotation to substitute a different verifier for
it, because that comparison is the whole job of `PrepAndExpectedTestCase`.

Annotation values require compile-time constants — a `static final
String[]`, `VerifyTableDefinition[]`, or `Properties` cannot be referenced
directly (JLS 9.7.1). A catalog class (<<catalog>>) or a composed annotation
(<<composed>>) is the way to share such values; each is described above.

The harder limit is structural, not a missing escape hatch: an annotation
is fixed at compile time on one method, and Java offers no mechanism for
one to vary per invocation. A `@ParameterizedTest` whose `VerifyTableDefinition[]`/
prep files/expected files change per `@MethodSource` row — the dominant
pattern in larger functional test suite scenarios — cannot be expressed with these
annotations *at all*. The programmatic `runTest()` API on
link:PrepAndExpectedTestCase.html[PrepAndExpectedTestCase] remains the
right and fully supported tool for that case, and for suites that layer
non-dbUnit assertions (exit codes, exception types, notification content)
around the dbUnit portion of a test. Its
link:PrepAndExpectedTestCase.html#Bundling_Test_Data[PrepAndExpectedTestData]
overloads keep the per-row prep/expected/verify triple to a single
`@MethodSource` column and a single method parameter.

`@DbUnitTestCase` field injection still helps such suites, even without the
lifecycle annotations: it makes the harness wiring explicit on the field
instead of inherited from a superclass, and a shared catalog (<<catalog>>)
gives the `VerifyTableDefinition` constants a first-class home that
non-parameterized tests in the same suite can point at by name.

`DbUnitOperation` is also narrower than `DatabaseOperation`: it covers the eight simple
operations only, with no declarative way to compose them (`CompositeOperation`) or wrap one
in a transaction (`TransactionOperation`). A test needing either drops to the programmatic
path the same way — configure the tester's setup/teardown operation directly in a
`@BeforeEach` method, on either path as long as no annotation declares that operation, or
override it on an injected `PrepAndExpectedTestCase`.
