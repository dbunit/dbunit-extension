= IOperationListener

[#overview]
== Overview

link:../apidocs/org/dbunit/IOperationListener.html[IOperationListener] (`org.dbunit`,
since 2.4.4) observes an link:../connections.html[IDatabaseConnection]'s lifecycle
around an link:../testcases/IDatabaseTester.html[IDatabaseTester]'s `onSetup()`/
`onTearDown()` calls. Set one with `IDatabaseTester.setOperationListener()`. This page
is the class-shape reference; see
link:../testcases/IDatabaseTester.html#IOperationListenerHooks[the IDatabaseTester
guide] for how the 3 hooks fit into the setup/teardown lifecycle in practice.

[#hooks]
== The 3 Hook Methods

[cols="2,3", options="header"]
|===
|Method |Called

|`connectionRetrieved(IDatabaseConnection connection)` |Immediately after a connection is newly created or an existing one is retrieved, before the operation runs. Apply `DatabaseConfig` customizations here.
|`operationSetUpFinished(IDatabaseConnection connection)` |After the operation of `IDatabaseTester.onSetup()` completes, or fails - including when `connectionRetrieved()` itself threw.
|`operationTearDownFinished(IDatabaseConnection connection)` |After the operation of `IDatabaseTester.onTearDown()` completes, or fails - including when `connectionRetrieved()` itself threw.
|===

Both `*Finished` methods exist so a listener can decide whether the connection should
be closed at that point — the two built-in implementations below make opposite choices.

[#defaultoperationlistener]
== DefaultOperationListener

link:../apidocs/org/dbunit/DefaultOperationListener.html[DefaultOperationListener] is the
default implementation used when none is explicitly set. Confirmed directly against its
source: `connectionRetrieved()` is a no-op; both `operationSetUpFinished()` and
`operationTearDownFinished()` close the connection. In other words, a fresh connection
is created (or retrieved) for every single `onSetup()`/`onTearDown()` call unless a
different listener is configured.

[#noop]
== IOperationListener.NO_OP_OPERATION_LISTENER

`IOperationListener.NO_OP_OPERATION_LISTENER` is a static, trace-logging implementation
that never closes the connection. Use it (or a custom non-closing listener) whenever a
connection needs to survive past a single `onSetup()`/`onTearDown()` call — most
commonly when pairing an `IDatabaseTester` with a
link:../connections.html#cachingconnectionprovider[CachingConnectionProvider], which
would otherwise have its cached connection closed out from under it after the very
first use:

[source,java]
----
databaseTester.setOperationListener(IOperationListener.NO_OP_OPERATION_LISTENER);
----

[#custom]
== Writing a Custom Listener

A custom listener isn't limited to open/close decisions — since every hook receives the
live `IDatabaseConnection`, it's a convenient place for cross-cutting setup/teardown
concerns such as logging or metrics:

[source,java]
----
IOperationListener listener = new IOperationListener()
{
    public void connectionRetrieved(IDatabaseConnection connection)
    {
        log.debug("Connection retrieved: {}", connection);
    }

    public void operationSetUpFinished(IDatabaseConnection connection)
    {
        log.debug("Setup finished for: {}", connection);
    }

    public void operationTearDownFinished(IDatabaseConnection connection)
    {
        log.debug("Teardown finished for: {}", connection);
    }
};
databaseTester.setOperationListener(listener);
----

[#extension]
== Under the JUnit Jupiter Extension

link:../testcases/DbUnitExtension.html[`DbUnitExtension`] leaves the listener of the tester of an
annotation-driven test alone: that test runs through a `DefaultPrepAndExpectedTestCase`, which
only reads the tester, so a tester shared across test methods carries nothing from one test to
the next. On a plain `@ExtendWith(DbUnitExtension.class)` test, the 3.5.0 style, the extension
wraps the tester's listener for the duration of one test, then puts the tester's own listener
back. The wrapper only forwards every callback to your listener, closes included, and takes the
row count baseline from the connection `onSetup()` retrieves, so capturing it opens no
connection of its own. That connection stays your listener's to close or to keep open, so
a non-closing listener still keeps a fixed connection alive for the next test. The extension
closes only a connection it resolves itself, and not one that a tester known to hand out one
fixed connection handed out, as a `DefaultDatabaseTester` does and a `JdbcDatabaseTester`,
`DataSourceDatabaseTester` or `JndiDatabaseTester` built with a `CachingConnectionProvider`
does, nor one of a tester whose listener is `NO_OP_OPERATION_LISTENER`; those stay open for
their owner. With the row count check enabled it
resolves one to verify after `onTearDown()` when your listener closed the one `onSetup()`
retrieved, as the default listener does. Wrapping the listener and putting it back rely on the
tester reporting it through `getOperationListener()`, as `AbstractDatabaseTester` and the
testers built on it do, never returning `null`: a tester nobody gave a listener reports the
default one it would use. A
custom `IDatabaseTester` that does not override it reports none, so the extension leaves
its listener exactly as configured rather than replace it with one it could not put back.
For such a tester the row count check baseline is captured from a connection of its own before
`onSetup()`.

* A connection the extension resolves itself, rather than through the tester's
`onSetup()` or `onTearDown()`, is first offered to your listener's
`connectionRetrieved()`, so a `DatabaseConfig` customization made there, such as
enabling the link:rowcountcheck.html[row count check], applies to it too. That includes
the connection a plain `@ExtendWith(DbUnitExtension.class)` test resolves for the row
count baseline when `onSetup()` cannot be relied on to retrieve one, a `NONE` setup
operation, say, and the one it resolves to verify the baseline after `onTearDown()` when
your listener closed the connection `onSetup()` retrieved. An annotation-driven test never
calls `onSetup()` or `onTearDown()`: its
`DefaultPrepAndExpectedTestCase` offers your listener's `connectionRetrieved()` the shared
connection when it acquires it, before the row count baseline or anything else reads the
connection's configuration, and again each time it runs a set up or tear down operation, but
never the `*Finished` callbacks, as that class decides when its shared connection closes. The
same connection can be offered more than once, and on a plain test by the extension and again
when `onSetup()` retrieves it, so keep `connectionRetrieved()` idempotent, as configuring a
`DatabaseConfig` is.
