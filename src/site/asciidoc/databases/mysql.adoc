= MySQL

== Overview

`org.dbunit.ext.mysql` provides MySQL-specific type recognition and
metadata handling for dbUnit. See link:mariadb.html[MariaDB] for MariaDB,
which has its own dedicated factory and reuses MySQL's metadata handling.

== IDataTypeFactory

link:../apidocs/org/dbunit/ext/mysql/MySqlDataTypeFactory.html[MySqlDataTypeFactory]
handles several MySQL-specific mappings: `longtext` as `CLOB`, `bit` as
`BOOLEAN` (MySQL 5.0+) or `TINYINT` depending on context, `point` as
`BINARY`, and the `UNSIGNED` integer family (e.g. an unsigned `INTEGER`
needs `BIGINT` to hold its full range without overflow — see MySQL
Connector/J's
https://dev.mysql.com/doc/connector-j/en/connector-j-reference-type-conversions.html[type
conversion reference]). Register it via
`DatabaseConfig.PROPERTY_DATATYPE_FACTORY` — see
link:../properties.html#typefactory[Properties] and
link:../connections.html[Connections & Configuration].

== IMetadataHandler

link:../apidocs/org/dbunit/ext/mysql/MySqlMetadataHandler.html[MySqlMetadataHandler]
fixes qualified-table-name matching (link:../properties.html#qualifiedtablenames[the
qualified table names feature]) for MySQL, where the default handler's
catalog/schema comparison doesn't line up with how MySQL reports them.
Symptom without it: a `NoSuchColumnException` for a column you can see
exists.

`MySqlMetadataHandler` passes a schema to the driver as the JDBC catalog,
which is how MySQL Connector/J reports a database. An empty schema, as in
`new DatabaseConnection(jdbcConnection, "")`, means the database the
connection works in: since 3.6.0 the handler passes that database as the
catalog, as MySQL Connector/J lists no tables at all for an empty catalog.
A `null` schema still searches every catalog the user can see, as described
below.

For a connection not restricted to a single schema — e.g. connecting as
`root` specifically to work across several schemas at once — use
link:../apidocs/org/dbunit/ext/mysql/MultiSchemaMySqlMetadataHandler.html[MultiSchemaMySqlMetadataHandler]
instead. Without a schema, `MySqlMetadataHandler` passes a `null` catalog
to the driver, which under Connector/J 8.0 and later lists the tables of every
catalog the user can see. Most tables of MySQL's system catalogs are reported
as `SYSTEM TABLE` or `SYSTEM VIEW` and stay out of a dataset, but not all: for
`root`, the `sys_config` table of the `sys` catalog comes back as an ordinary
table. Only with the driver's `nullCatalogMeansCurrent` property set to
`true`, its default in Connector/J 5.1, does a `null` catalog mean the
connection's current catalog, so `MySqlMetadataHandler` alone can silently
hide tables in every schema but one, surfacing as `NoSuchTableException` for
a table you can see exists. `MultiSchemaMySqlMetadataHandler` never passes a
`null` catalog: it enumerates the catalogs the connection can see, skips
`information_schema`, `mysql`, `performance_schema` and `sys`, and unions the
results across the rest itself, so it lists the same tables whatever
`nullCatalogMeansCurrent` is set to. Pair it with
link:../properties.html#qualifiedtablenames[the qualified table names
feature] so same-named tables in different schemas stay distinguishable.

== Connection Preconfiguration Class

link:../apidocs/org/dbunit/ext/mysql/MySqlConnection.html[MySqlConnection]
wraps a JDBC `Connection` and pre-registers both `MySqlDataTypeFactory` and
`MySqlMetadataHandler`:

[source,java]
----
IDatabaseConnection connection = new MySqlConnection(jdbcConnection, schema);
----

== Vendor-Specific Types

The `longtext`/`bit`/`point`/`UNSIGNED` handling above; otherwise standard
SQL types.

== Known Quirks

Forgetting to register `MySqlMetadataHandler` is the most common cause of a
spurious `NoSuchColumnException` on MySQL. See the FAQ:
link:../faq.html#NoSuchColumnException[Why am I getting a "NoSuchColumnException"
but I am sure that the column actually exists?]
